Unit 1
Physical quantities and executable models

Introduction

Suppose a message says that a small vehicle travelled “240 in 12”. There is arithmetic we could do with those numbers, but we do not yet have a useful description of motion. Is the distance in millimetres or metres? Is 12 a duration in seconds, or the reading on a clock? What exactly was taken to be the vehicle’s position?

These are not details to add after a calculation. They determine which calculation answers the question. A physical description connects numbers with quantities, units, reference choices and assumptions. Once those connections are clear, quite elementary mathematics can tell us a great deal. Without them, a more elaborate calculation may simply make an ambiguous statement look authoritative.

This unit takes us from a carefully specified quantity to a small program that evaluates a physical model. We will not begin with a large simulation. Instead, we will use a model simple enough to follow by hand, so that every line of code can be connected with an idea we understand.

From a quantity to a prediction

The first lesson asks what a measurement statement means. You will distinguish the quantity itself from its numerical value, change units without changing the quantity, and use dimensions to expose some impossible equations. Scientific notation and rough estimates will help you judge whether a result is on a plausible scale.

Next we will describe position along a line and make time intervals explicit. If an object’s position changes at a constant rate, we can use its starting position and the elapsed time to predict a later position. The assumption is deliberately simple. Its simplicity gives us room to ask useful questions: what happens if the elapsed time is zero, how does the sign of the rate affect the result, and how far beyond the original situation should we trust the prediction?

Writing that calculation in Python brings the assumptions into a new form. A variable name is a place to make a quantity’s meaning visible. A condition can reject an input that makes no sense for the question. A function can express the same model for several different inputs. These are programming ideas, but we will teach them through physical tasks rather than as an unrelated collection of commands.

A calculation that can be inspected

A notebook can contain an explanation, the input values, the calculation and the result in one place. That is an advantage only if the pieces agree. If a heading says “metres” but the values are in centimetres, or an old output remains below a changed input, the notebook can mislead its reader. You will therefore learn to state units explicitly, compare with a hand calculation and rerun the whole calculation from a clean starting state.

Ordinary Python numbers do not carry physical units automatically. We will initially keep the unit convention in names and text, and calculate using values in agreed units. This approach is transparent, but it places a responsibility on us: a computer will happily combine two numbers even when their physical meanings make the operation inappropriate.

At the end of the unit you will assemble a short executable model and work through a mixed exercise set that returns to quantities, units, assumptions and code. Unit 2 will then examine the inputs more closely. A value written as a measurement is not the end of the story: we need to ask how it was obtained, why another reading might differ and what precision is justified.

Allow about 18 hours for the complete unit, including eight hours of programming work. The first lesson, including this introduction, has a three-hour allocation and needs only paper and a calculator. The separate practical orientation helps you prepare a notebook environment before the programming begins in Lesson 2. You can read the first lesson before doing that setup.

There is no requirement to finish a particular M101 lesson before starting. Simple algebra and arithmetic are enough here, with reminders where useful. If you already program, use the explanations to inspect your habits rather than treating familiar syntax as new: do your names communicate units, can you explain a result without rerunning it, and have you separated a check of the program from a check of the physical model?
