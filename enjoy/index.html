Enjoy the full experience

Anyone can use this website as it is to read the published learning materials, try the public activities and download the available study resources. No account or setup is needed.

You can also discuss the lessons with your own AI tutor in another app and get most of the experience without creating an account if you are not interested in keeping records or issuing (self-accredited) certificates.

Your GitHub sign-in worked. This installation's private workspace belongs to its owner, so signing in here does not create your own student workspace. You are welcome to keep using all the public learning materials.

What would you be missing?

Using this shared site does not give you a private place here to:

  • Save your profile, Academic Journal and personal study records.
  • Keep your own submitted work, tutor feedback and archived tutorial conversations.
  • Connect your agent to read and save those records as your tutor.
  • Manage personal timetable and progress features where supported, or generate proof packages from your own academic archive.

Your conversations in another app are not automatically saved here, and this site's owner-only records remain private. Signing in with a different GitHub account does not unlock these features.

A tutor alongside you

LibraUni is designed to be used with an AI agent as your personal tutor: exploring ideas together, working through difficulties and, once connected to your workspace, helping you keep a record of your learning. The site also offers optional tools to record proof of your academic activity on the blockchain. The empowering shift is that you can build a sustained education around your own questions and ambitions, with individual support at your own pace. You stay in charge of the direction—and do the thinking that makes it yours.

Want a workspace of your own?

The guide below shows how to create a separate copy with your own accounts, private database and authorised AI tutor. You can keep using the public materials without doing any of this.

This is a guided setup, not an instant sign-up. Cloning the website does not connect your tutor, copy the owner's private records or make unfinished teaching and timetable features available.

STEP 1

Prepare your accounts

You need a GitHub account for the website and sign-in, a Google account for Firebase, and an AI agent that can read and edit local files and run development tools. A chat-only assistant can discuss lessons, but cannot automatically save your work to this system without a connection you set up.

You make account, permission and payment decisions; your agent can handle the code and checks. Review your chosen providers' current plans and usage limits. AI use, hosting, database storage and backups may have costs. Ethereum is optional and is not required to study or save a journal.

A setup brief to give your agent

Copy this into your agent, then work through the steps together. Give project identifiers when asked; enter passwords and secrets through the provider's sign-in or secure configuration screens.

Ready when: you have the accounts and an agent able to help with the technical setup.

STEP 2

Create your own copy

  1. Open the public website repository and fork it into your GitHub account. Clone your fork to your computer.
  2. For the simplest address, name the repository YOUR-USERNAME.github.io. This project uses links beginning with /, so hosting it under a subfolder needs additional routing and asset changes. If you already have a user site, ask your agent to plan the address before continuing.
  3. Create a separate private repository or private backed-up folder for learner files. Keep it outside the public website folder.
  4. Before publishing, replace the LibraUni name, logo and reserved visual identity with your own, unless you have permission to use them. Retain required code notices, credit teaching material and preserve its reuse terms and third-party credits. See Licence & reuse.

A public fork includes public code, teaching and commit history, not the owner's private database or private backup repository. Never copy someone else's learner records. Historical instructions in AGENTS.md are not your biography, study progress or authority to access their services.

Ready when: you have your own website repository, a separate private workspace and a plan for your site's identity.

STEP 3

Set up private storage and GitHub sign-in

  1. In the Firebase console, create your own project and register a web app. Save its web configuration for the next step.
  2. Create the default Cloud Firestore database in Standard edition, choosing a suitable location. Start with production-mode rules; deploy the adapted owner-only rules before using the site. Do not leave the database open in test mode.
  3. Enable GitHub in Firebase Authentication. In GitHub's developer settings, create an OAuth App for your site. Use the exact callback URL shown by Firebase, normally https://YOUR-PROJECT.firebaseapp.com/__/auth/handler.
  4. Enter the OAuth client ID and secret in Firebase's GitHub-provider configuration. Add your website hostname to Authentication's authorised domains. Add your local test hostname explicitly if you need local sign-in.

The Firebase web configuration belongs in the website code; the OAuth client secret, administrator credentials and account recovery codes do not.

Official instructions: Create a Firestore database · Configure GitHub authentication.

Ready when: your own project, database and GitHub sign-in provider exist.

STEP 4

Connect the copy to your accounts

Ask your agent to make the following changes in your fork. This is the point where a copy becomes your installation.

Configuration checklist for your agent
  • Replace src/firebase-config.js with your web app's configuration; update the project alias in .firebaserc.
  • Replace the original GitHub numeric owner ID in src/planner-store.js and firestore.rules with yours. Obtain it from your authenticated GitHub account or https://api.github.com/users/YOUR-USERNAME. A GitHub numeric ID is different from the Firebase user UID. Preserve the rule requiring the signed-in Firebase UID to match the requested user path.
  • Update owner fixtures in security-tests/firestore.test.js, retaining tests for rejected anonymous and other-account access. Keep data validation, revision checks and immutable histories.
  • Review scripts/archive-academic-session.mjs and scripts/archive-student-records.mjs: their database URLs currently name the original project. Configure your project before any upload.
  • Update the repository reference in scripts/render-evidence-release.mjs so evidence identifies your actual teaching release. Review deployment settings, brand assets, source attribution and any other installation-specific links. Do not blindly replace licence credits or stable record-format identifiers.
  • Replace inherited personal instructions with your own private tutoring instructions. Set public/backup-health.json to report unconfigured until your own backup setup has been verified.

Deploy rules to your Firebase project, separately from publishing the website. Your agent can use the Firebase CLI with an explicit project target:

firebase deploy --only firestore:rules --project YOUR_PROJECT_ID

Firebase's rules deployment guide. Never “fix” an access error by allowing everyone to read or write.

Ready when: the site and its access rules identify your project and your account, with no upload path targeting the original owner's database.

STEP 5

Test, then publish your website

The repository currently uses Node 24 and pnpm 11.19.0. Your agent should check the current workflow when you make your copy, install its dependencies and run:

pnpm install --frozen-lockfile
pnpm test
pnpm build
pnpm dev

Run the Firestore security tests too, using Java 21 and the Firebase CLI. This command targets an isolated demo project:

firebase emulators:exec --only firestore --config firebase.test.json --project demo-librauni 'pnpm test:rules'

After local checks, enable Actions in your fork and choose GitHub Actions under repository Settings → Pages. Review the existing Pages workflow, then push your approved changes to your own main branch. Wait for both the security job and publication to succeed. GitHub's Pages setup guide explains the hosting steps.

On the published site, sign in, open My profile and save a small test value. Reload it in another browser. Create a clearly labelled test journal entry and confirm that it persists. Verify that signing out hides private records and that another account cannot read or write them. Save the profile before connecting the tutor: the current upload scripts expect exactly one saved learner profile.

Ready when: your copy works online, saves only to your database and passes the isolation checks.

STEP 6

Give your tutor a verified connection

The AI tutor runs in your chosen agent application, outside the website. Website sign-in does not give it database access or automatically archive your conversations. Choose what it may read and save, and establish that connection explicitly.

Keep your learner instructions, working files and session records in the private workspace. Ask the tutor to read the current teaching standards and relevant lesson, explain ideas, review your attempts and distinguish demonstrated understanding from confidence or attendance. It should record substantive learning, preserve originals and append corrections; it should not log website maintenance as academic progress.

Connect and test the existing upload tools
  1. Authenticate the Firebase CLI locally with an account authorised for your project. Restrict its Google Cloud permissions appropriately. These scripts use Google credentials and IAM access, which is separate from browser sign-in and can bypass Firestore client rules. Read Firebase's REST authentication guidance before granting access.
  2. Have your agent inspect both upload scripts and their input schemas. Set FIREBASE_AUTH_MODULE to the installed Firebase CLI's lib/auth.js path. This integration uses a CLI internal module; check compatibility with your installed version. It is not a ready-made universal agent connector.
  3. Confirm the scripts target your project and the profile belongs to your Firebase user. Keep manifests, originals and credentials outside the public repository. Do not give an agent a token for the original LibraUni project.
  4. Prepare a clearly labelled test session and small test file. Run each script without --write first. After reviewing the target and validated input, run with --write. Read back the journal entry and verify that the downloaded original matches the uploaded file.
node scripts/archive-academic-session.mjs /PRIVATE/session.json
node scripts/archive-student-records.mjs /PRIVATE/manifest.json

The input formats are documented in the scripts and the repository's docs/academic-journal.md, docs/academic-record-quality.md and docs/learning-evidence.md. A new chat may not inherit access: keep a private handover and have the agent verify its connection each time.

If your agent cannot connect, you can still study and use the Journal's optional manual-entry and transcript-import tools. That is a fallback, not automatic tutor logging. The agent must tell you what it has saved and what remains only in the conversation.

Give your tutor a lasting set of instructions

A database connection is only the start. Your agent also needs to know how to teach, assess and maintain your records. Ask it to create a versioned tutor handbook in your private workspace, using the repository's current teaching standards and record documentation. Keep your learner details separate from reusable instructions. This guide provides a starting brief; it does not yet supply a complete, tested tutoring and assessment handbook.

The handbook should cover:

  • Teaching: explain ideas, ask questions, review your reasoning and offer progressively stronger hints. Help you develop independence, rather than completing assessed work for you.
  • Context: read the curriculum, prerequisites, available lessons and your latest saved records. Know how Student Home, Academic Journal and On-chain certificate fit together. Distinguish released teaching from outlines and plans.
  • Session records: save substantive learning, evidence of understanding, difficulties and next steps in your Academic Journal. Preserve original submissions, feedback and accessible tutorial transcripts; append corrections. Confirm saves by reading them back and report anything missing. Website maintenance is not academic progress.
  • Assessment: use the approved task, rubric and permitted-assistance rules for each tutor-marked assignment (TMA), interactive computer-marked assignment (iCMA) and exam. Keep guided practice separate from independent attempts. Check marking, explain feedback, preserve assessment versions and record corrections or reassessment. Do not claim exam supervision or independent authorship that has not been verified.
  • Certificates: check agreed completion criteria against saved evidence before preparing a certificate. If criteria, assessments or an issuing process are missing, identify the gap instead of inventing an award. A self-issued certificate is not an accredited qualification; blockchain proof does not validate marks or mastery. Wallet transactions require your approval.
  • Continuity: keep a short private handover with your current lesson, open questions, saved-record references and next step. Each new chat must read it and verify access. Tutor instructions do not authorise changes to the website, account permissions or publication.
A first-session brief to give your tutor

Use this after setup. Tell the agent where your local website repository and private workspace are; do not paste credentials into the prompt.

For later chats, give the agent the location of your handbook and handover, then start with: “Read my tutor handbook and latest handover, verify your connection to my private records, and help me continue from my last session.” A new chat does not automatically remember the previous one.

Ready when: your tutor has demonstrated a successful private save and read-back, reviewed its handbook with you, and clearly identified any assessment or certificate rules still to be agreed.

STEP 7

Protect your work

Saved online work is available when you sign in on another computer. Files or drafts that have never been uploaded are not. Keep account recovery codes separately from your study computer.

The original owner's private backup service is not included in this public repository. Ask your agent to set up your own backup and recovery process. It must cover database subcollections and original-file chunks, preserve versions, and verify a restore in an isolated test location. The current installation excludes profile data from backup; decide and document your own policy rather than assuming it is included.

A private GitHub backup repository is one option. It requires its own scheduled workflow and permissions; use a read-only backup identity, with recovery permissions kept separate. GitHub documents short-lived Google Cloud authentication for Actions. The private scripts used by this site's owner are not publicly available, so your agent must implement and test an equivalent process or configure a suitable backup service.

The Academic Journal's text download is a readable copy, not a database restore. On-chain certificate can download saved academic originals and proof data; Ethereum anchoring is optional and is not a backup of the files themselves. Confirm the latest successful backup, not just the presence of a schedule.

Ready when: a backup and isolated restore have been verified, with private recovery instructions you can access from another computer.

STEP 8

Begin with one real study session

Choose an available lesson. Tell your tutor what you are studying, show your reasoning and ask it to help you work through difficulties. Start with the tutor handbook and starting brief above. At the end, have it save an evidence-based journal entry, archive any original work and update your private handover. Open Academic Journal to confirm the record is there.

Copying the site does not complete the curriculum or unlock unavailable timetables. New material can always be in development. Enrolment and automated degree-wide progress tracking are not complete. AI tutoring and any recorded achievements do not create an accredited university qualification.

Keep your installation updated deliberately: review upstream changes, test them locally and preserve your own configuration and records. Do not let an update replace your account settings with the original owner's.

You are ready: your site, your private records and your tutor work together—and you know what has actually been saved.

If something does not work

Sign-in succeeds, but access is denied
Check the GitHub numeric owner ID in the client and deployed rules, the Firebase project and the Firebase user path. Do not weaken access rules.
The sign-in window reports an unauthorised domain
Check Firebase authorised domains and the OAuth callback URL against your own site's configuration.
The homepage loads, but other pages or images fail
Check whether you used a subfolder address despite the site's root-relative links.
The agent cannot save, or finds no learner profile
Check its project target, local authorisation, CLI compatibility and your saved profile. A successful browser login does not authorise the agent.
There is no record of a conversation
Confirm it was actually archived. The website cannot automatically read chats from another application.
