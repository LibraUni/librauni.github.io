Lesson 5
Functions and checks you can explain

A calculation becomes more useful when we can give it new inputs without rewriting its instructions. A calculation becomes more trustworthy when we can explain what it promises, what we have checked and what remains an assumption. In this lesson we bring those two ideas together.

Lesson 4 used a condition to select valid requests and a loop to calculate several positions. The same motion formula appeared wherever a prediction was needed. Copying that formula works for a small experiment, but it creates several places where a later correction could be missed. We will give the calculation a name, make its inputs explicit and return a result that another part of the program can use.

Allow three hours, including two hours of Python in the Lesson 5 notebook. Its activities are the ones in this reading, not additional work. The Python companion contains the worked examples. No packages or testing framework are required. Predict results on paper before running them, and keep explanations alongside the code. All numerical motion cases below are stipulated teaching examples.

1.25 Give a calculation explicit inputs

Imagine changing the trolley's initial position. In our previous program we would edit its input assignment and rerun the calculation. Now imagine comparing two trolleys, or using the same calculation in another notebook. We want to specify each case at the point where we ask for its prediction, while keeping one readable definition of the calculation itself.

A Python function is a named group of instructions that we can call. A call supplies arguments: the particular input values for that use. The definition names parameters: the names through which the function's body will use those supplied values. A parameter is therefore a role in the definition; an argument is what fills that role in a particular call.

Our physical model remains

x=x0+v(t−t0)

Positions use a fixed origin and positive direction; the signed rate is constant over the interval considered. We use metres, seconds and metres per second. As in Lesson 4, our stated motion case is known only from the initial event onwards. The calling code will check that time condition before asking the function for a prediction. The function below performs the arithmetic; it does not enforce the condition by itself.

Example 1.23 · Define once, call with a case

def position_m(x0_m, v_m_per_s, t0_s, t_s):
    """Return position in metres for a constant signed rate.

    Caller supplies finite numbers in m, m/s and s,
    with t_s >= t0_s and common position/time origins.
    """
    elapsed_s = t_s - t0_s
    return x0_m + v_m_per_s * elapsed_s

prediction_m = position_m(-2.0, 0.75, 12.0, 20.0)
print("Position / m:", prediction_m)

The result is Position / m: 4.0. Eight seconds elapse; at +0.75 m/s the displacement is +6 m, giving a position of −2 m + 6 m = +4 m. The answer agrees with the earlier trolley calculation because we have reorganised the instructions, not changed the physical relationship.

The keyword def begins the definition. The function name is followed by its parameters in parentheses and a colon. The indented lines belong to the function; four spaces make this structure visible. The text enclosed in triple quotes is a docstring, a description stored with the function. It describes units and responsibilities but does not perform any checks. The next two lines calculate the duration and return the predicted number.

Executing the definition creates the function. It does not yet calculate a trolley position. The unindented assignment below it makes a call. Here arguments match parameters from left to right: −2.0 becomes the local value of x0_m, 0.75 of v_m_per_s, 12.0 of t0_s and 20.0 of t_s. Python evaluates the body, then places the returned value where the call appeared. The assignment gives that value the name prediction_m.

With four numerical arguments, a positional call is easy to misread. We may instead name the parameters in the call: position_m(x0_m=-2.0, v_m_per_s=0.75, t0_s=12.0, t_s=20.0). These are keyword arguments. The names identify the intended roles, so their order may change. Here = supplies an argument by name; it does not assign a new outside variable. We will use both forms, keeping all four arguments explicit. A misspelled keyword or a missing required argument produces an error, not a guessed value.

1.26 Return a result that can travel

The distinction between returning and displaying becomes important as soon as a result has another use. Suppose we want a list of positions for a graph later in the module. Numbers printed on the screen do not automatically enter that list. The caller needs a value it can pass to append. A return statement supplies that value; a print call writes a display.

Within a function, return also ends that call immediately. Statements later in the same execution path are not run. Execution resumes in the calling code. A function that reaches its end without an explicit returned value returns None, Python's special value for the absence of a result value. None is neither zero nor an empty string. It cannot serve as a numerical position.

Example 1.24 · A visible number is not necessarily the result

def display_displacement_m(v_m_per_s, elapsed_s):
    print(v_m_per_s * elapsed_s)

saved_m = display_displacement_m(0.75, 8.0)
print("Saved value:", saved_m)

Two lines appear:

6.0
Saved value: None

The first line came from the print inside the function. The assignment received the function's returned value, which is None because the function reached its end without returning a number. Assigning the call does not capture its printed text.

For a displacement that can be reused, define and call this version:

def displacement_m(v_m_per_s, elapsed_s):
    """Return signed displacement in metres; duration is in seconds."""
    return v_m_per_s * elapsed_s

saved_m = displacement_m(0.75, 8.0)
print("Displacement / m:", saved_m)
print("Position / m:", -2.0 + saved_m)

Now the outputs are Displacement / m: 6.0 and Position / m: 4.0. The caller controls both the labels and the use of the returned value.

A function may legitimately print, return or do both. We are choosing to keep our numerical model function quiet so that it works equally well in a single calculation or inside a loop. Separating calculation from display also lets us compare the numerical result directly with an expected value. It avoids having to recover a number from a sentence intended for a reader.

A notebook can display the value of its last expression even without print. Thus a bare call to position_m(...) may visibly produce a number in a notebook while doing nothing visible in a script. That is the notebook displaying the returned value, not the function printing. An assignment normally suppresses that automatic display; the value is still available under its assigned name.

None signals that no result value was supplied, so replacing it with zero would hide a programming defect.

1.27 Keep each call's working separate

In Lesson 3 an assignment could leave a stale result elsewhere in the notebook. A function helps by bringing the dependent calculations together. Every call to position_m calculates a new duration from that call's inputs before returning a position. It also gives its intermediate names a limited scope: the part of the program in which those names belong.

The parameters and the name elapsed_s in our definition are local to a call. An outside name with the same spelling is a different binding. For these numeric inputs, assigning a new number to a local parameter or intermediate name does not assign that number to a name in the caller. We can see this without deliberately causing an error.

Example 1.25 · Same spelling, different working

def duration_s(start_s, end_s):
    elapsed_s = end_s - start_s
    return elapsed_s

elapsed_s = 999.0
first_s = duration_s(12.0, 20.0)
second_s = duration_s(5.0, 9.0)
print("First duration / s:", first_s)
print("Second duration / s:", second_s)
print("Outside value:", elapsed_s)

The printed values are 8.0, 4.0 and 999.0. Each call calculates and returns its own duration. The outside assignment was deliberately chosen to be conspicuously different; it is not used by this function.

That qualification matters. Lesson 4 showed that two names can refer to the same mutable list. Passing such a list to a function does not automatically protect it from a method such as append inside the function. We will avoid changing input lists here. Our model takes scalar numbers and returns a scalar number; it has no need to modify a caller's collection.

Nor are functions sealed away from everything outside them. Python can read an outside name if the name is not local. A function that reads a notebook variable called speed without accepting it as an input may therefore change behaviour after an unrelated cell changes speed. For our reusable calculation, passing all four physical inputs explicitly makes that dependency visible. A short parameter list is not an advantage if it conceals information on which the answer depends.

There is still an execution-order responsibility. Editing a function's definition in a notebook does not replace the function already held by the kernel until the definition cell is executed again. Calls made before that rerun may use the old body. Save, restart and run from the top after making changes; inspect results as well as the absence of errors.

1.28 Choose checks that could reveal a mistake

We have checked the function against one hand calculation. That is useful evidence, but a mistake can agree with a carefully chosen example by accident. If every trial starts at clock reading zero, a function using v_m_per_s * t_s instead of v_m_per_s * (t_s - t0_s) will appear correct. Good checks include cases in which plausible mistakes would give different answers.

Start by writing the expected result independently, before running the function. For the trolley, an ordinary case checks the combined arithmetic. The initial event checks that no displacement is added when no time has elapsed. A zero rate checks that the initial position remains unchanged at a later time. A negative rate checks the sign convention. These cases ask different questions even when some answers happen to match.

Example 1.26 · A check with an independent answer

Using the function defined in Example 1.23, compare its ordinary prediction with the hand result +4 m:

actual_m = position_m(-2.0, 0.75, 12.0, 20.0)
expected_m = 4.0
print("Actual / m:", actual_m)
print("Expected / m:", expected_m)
print("Difference / m:", actual_m - expected_m)
print("Exact agreement for this case:", actual_m == expected_m)

The difference is 0.0 and the comparison is True. Here the inputs and intermediate values have exact binary representations at these magnitudes, so exact comparison is suitable. Lesson 3 showed why general decimal calculations need more care: a tiny rounding difference is not automatically a faulty physical equation. Later numerical work will define appropriate tolerances. Do not “fix” a disagreement by rounding everything until the check passes.

To see why the nonzero time origin matters, examine the deliberately wrong expression x0_m + v_m_per_s * t_s. For the ordinary row it gives −2 + 0.75 × 20 = 13 m rather than 4 m. At the initial event it gives 7 m rather than −2 m. Yet it passes the zero-rate row. One successful check therefore cannot replace several checks chosen to discriminate between possible implementations.

Do not obtain the expected value by copying the very same expression into a second line and calling that a test. Both lines can share the same mistake. Use a hand calculation, a defining property or a genuinely different argument. If a check fails, retain the actual result and ask which dependency could explain the discrepancy. Changing the expected answer to match the program discards the evidence.

1.29 Keep the units and the promise together

Even a correct function can give a useless prediction when called with the wrong interpretation of an input. The suffix _s is a reminder to the reader; it does not attach a unit to a Python float. If a caller supplies a number of minutes where seconds are expected, the function cannot discover the mistake merely by examining the number.

Consider a separate stipulated motion: a point starts at +1 m at time zero and moves at +0.5 m/s. We want its position after two minutes. The calculation must first express the time in the convention used by the function:

2min×60smin=120s

The minute units cancel. The displacement is 60 m, so the predicted position is 61 m. This motion is an idealised case; we are not claiming that our earlier laboratory trolley can travel that far.

Example 1.27 · Correct arithmetic, wrong input meaning

requested_min = 2.0
wrong_m = position_m(1.0, 0.5, 0.0, requested_min)
requested_s = 60.0 * requested_min
correct_m = position_m(1.0, 0.5, 0.0, requested_s)
print("Minutes mistakenly supplied as seconds / m:", wrong_m)
print("After explicit conversion / m:", correct_m)

The first result is 2.0; the second is 61.0. The first call did exactly the arithmetic it was defined to do, interpreting its final argument as two seconds. Changing the output label to metres cannot repair an input-time error. Notice also that the final positions do not differ by a factor of 60, because both contain the same +1 m initial offset; their displacements do.

A useful function description acts as a small agreement between the caller and the calculation. It states what the inputs mean, what result will be returned and which conditions must hold. The caller is the code that invokes the function. Our caller is responsible for consistent units and origins, finite numeric values, and a requested time at or after the initial event. The physical application must also justify the constant signed rate. Merely writing those conditions in a docstring enforces none of them.

We retain Lesson 4's explicit time check outside the function. This keeps one numerical return type and uses only control flow already taught. A production library could instead enforce invalid-input handling inside its public function; that would require a deliberately designed failure response. Here an earlier request must be refused by the caller before calling position_m. Calling it directly with an earlier time still evaluates the formula, but falls outside this lesson's stated agreement. The result is not an authorised prediction for our forward-only case.

Three different questions

Implementation: does the code calculate the stated expression? Use: are inputs supplied according to the stated units and conditions? Physical suitability: is that expression an adequate model of the actual situation? Evidence for one question does not automatically answer the others.

Activity 1.32 · Diagnose the interface

For Example 1.27, predict the result if the caller supplies 0.5 minutes directly, and then after conversion to seconds. Calculate the displacements as well as the positions. Explain why the check t_s >= t0_s cannot detect this unit mismatch. Finally describe what would happen if someone directly called the function at −1 s with initial time zero, and what the intended caller should do instead. Allow about twenty minutes.

Discussion of Activity 1.32

Supplying 0.5 as seconds gives displacement 0.25 m and position 1.25 m. Half a minute is 30 s, giving displacement 15 m and position 16 m. Both numerical times are nonnegative, so both pass the lower-time-boundary comparison. That comparison knows nothing about the source unit. A direct call at −1 s gives the arithmetic value 0.5 m, but this earlier request violates our chosen domain. The intended caller should print an explicit refusal without calling the function. It should not substitute zero for the time or present the earlier result as valid.

1.30 Put a reusable calculation to work

We can now combine the parts without asking any one of them to do everything. The model function evaluates one case. The loop visits requested times. The condition enforces our declared lower time boundary. The caller pairs accepted times with returned positions and chooses the output messages. Reading the resulting program should reveal this division of responsibility.

Example 1.28 · Reuse the function inside a checked loop

Use the position_m definition from Example 1.23, then run:

x0_m = -2.0
v_m_per_s = 0.75
t0_s = 12.0
times_s = [20.0, 10.0, 12.0, 16.0]
accepted_times_s = []
positions_m = []

for t_s in times_s:
    if t_s >= t0_s:
        result_m = position_m(x0_m, v_m_per_s, t0_s, t_s)
        accepted_times_s.append(t_s)
        positions_m.append(result_m)
    else:
        print("No prediction at", t_s, "s: before initial event.")

print("Accepted times / s:", accepted_times_s)
print("Positions / m:", positions_m)

The 10 s request is refused. Accepted times are [20.0, 12.0, 16.0], paired with positions [4.0, -2.0, 1.0]. The two lists preserve the order of the requests. The function has no knowledge of those lists: each call returns one number, and the caller decides where it belongs.

Do not move the list initialisations inside the loop or append a refusal message to the numerical position list. Either change would break the meaning of the output. For an empty input list, the loop makes no calls and both result lists remain empty. A repeated valid request makes another call with the same inputs and gives another copy of the same result. These are intended consequences, not special cases to hide.

Activity 1.33 · Write and defend a small model function

Work independently before opening the discussion. A point starts at −1 m at clock reading 4 s and is stipulated to move at a constant signed rate of +0.25 m/s thereafter, relative to a fixed origin with positive direction right. Requested clock readings are [8.0, 3.0, 4.0, 12.0, 8.0]. Write your own returning position function with a short docstring, then a caller that rejects earlier times and preserves paired lists. Use explicit unit conventions.

Before running, predict every accepted pair and the refusal. Check the ordinary case at 12 s, the initial event, a zero-rate case at 12 s and a negative-rate case of −0.25 m/s at 12 s. Test an empty request list separately. Explain why the accepted position at 8 s must be retained even though it is zero. Finally state one physical circumstance under which the code could pass all these checks yet give unsuitable predictions. Save, restart, run from the top and inspect the results. Allow about thirty minutes.

Hint

Use the fixed initial position and time for every call. A valid result of zero is still a result: let the time condition decide whether to append it. Keep display outside the function and compute your expected answers by hand.

Discussion of Activity 1.33

The accepted times are [8.0, 4.0, 12.0, 8.0]; their durations are 4, 0, 8 and 4 s. The corresponding displacements are +1, 0, +2 and +1 m, giving positions [0.0, -1.0, 1.0, 0.0]. The 3 s request is refused. Here is one complete implementation:

def predict_position_m(x0_m, rate_m_per_s, t0_s, t_s):
    """Return position / m for a stipulated constant signed rate.

    Caller uses finite numbers in m, m/s and s, common origins,
    and checks t_s >= t0_s before calling.
    """
    duration_s = t_s - t0_s
    return x0_m + rate_m_per_s * duration_s

requests_s = [8.0, 3.0, 4.0, 12.0, 8.0]
accepted_s = []
positions_m = []
for request_s in requests_s:
    if request_s >= 4.0:
        predicted_m = predict_position_m(-1.0, 0.25, 4.0, request_s)
        accepted_s.append(request_s)
        positions_m.append(predicted_m)
    else:
        print("No prediction at", request_s, "s: before initial event.")
print("Accepted times / s:", accepted_s)
print("Positions / m:", positions_m)

The four independent checks give +1 m for the ordinary case, −1 m at the initial event, −1 m for zero rate and −3 m for the negative-rate case. Empty requests give empty lists with no refusal messages. Zero at 8 s is the position at the chosen origin, not absence of a result; both occurrences must be retained. A real object might accelerate or reach an end stop, violating the constant-rate assumption despite flawless implementation of the formula. Passing the checks does not settle that physical question.

We now have a small, explainable chain from a physical statement to reusable code: a model with units and conditions, a function with explicit inputs and a returned value, a caller that respects the agreement, and checks chosen for reasons we can state. Lesson 6 will bring these ideas together across the unit, with mixed practice and a compact reference. No additional programming syntax is needed to begin that consolidation.
