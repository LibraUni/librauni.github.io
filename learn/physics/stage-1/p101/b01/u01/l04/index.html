Lesson 4
Decisions and repeated calculations

A readable program can explain one prediction. A useful scientific program must also make clear when it will calculate, what it will do with an unsuitable input, and how it will keep track of several results. We now give our motion calculation those capabilities without changing the physical model.

Lesson 3 showed why the order of instructions matters. We will use that understanding twice: first to follow one of two paths through a calculation, then to run a sequence of instructions for each item in a list. A condition will express a choice that we can justify; a loop will repeat work that we can already explain by hand.

Allow three hours, including two hours in the Lesson 4 notebook. Its tasks are the activities below, not an additional set. The plain Python companion contains the runnable examples. Use a fresh working copy, predict before running, and finish with a clean restart and top-to-bottom execution. No new packages or particular M101 completion point are required.

1.19 Turn a condition into a question

Our trolley model starts with a position at a stated clock reading. So far we have chosen later times ourselves. Suppose we now ask the program to handle a collection of requests. One request might accidentally refer to an earlier time. Should the program return a number anyway?

The equation can be evaluated for a negative elapsed time. For a motion known to have the same constant rate before the initial event, that backward calculation could be meaningful. But our present case supplies the rate only from the initial event onwards. We will therefore adopt an explicit rule for this lesson: calculate at the initial event or later, and report an earlier request as outside the stated time domain. This is a modelling decision, not a ban on negative clock readings or a limitation of Python.

Let the initial clock reading be t0. The rule can be written

t≥t0⇔t−t0≥0

The double arrow means that the two conditions say the same thing. The second version uses the elapsed time already calculated in Lesson 3. Its equality boundary matters: zero elapsed time gives the initial position and is a useful check, so it belongs in our permitted cases.

Example 1.17 · Ask before calculating

t0_s = 12.0
t_s = 20.0
elapsed_s = t_s - t0_s
allowed = elapsed_s >= 0.0
print(allowed)
print(type(allowed))

The output is True, followed by <class 'bool'>. The comparison elapsed_s >= 0.0 asks whether the numerical duration is greater than or equal to zero. Its result is a Boolean value, either True or False; these are Python values with capital initial letters, not quoted messages. The assignment associates that result with allowed.

With t_s = 10.0, the duration is −2.0 and the comparison gives False. With t_s = 12.0, it gives True. The names still carry our unit convention: both clock readings are in seconds and use the same origin.

Python writes the familiar comparisons as >, <, >= and <=. Equality is tested with ==, and inequality with !=. A single = assigns a value; it does not ask a question. Thus allowed = elapsed_s >= 0.0 first performs a comparison, then stores its answer.

That stored answer is subject to the same rule as any result in Lesson 3. If you change elapsed_s, an earlier value of allowed does not update itself. Re-execute the comparison or put it directly in the decision we are about to write. Nor does True mean “the model is physically correct”: it means only that this particular numerical test passed. We are working with ordinary, finite numeric inputs in agreed units, not building a general-purpose data validator.

Discussion of Activity 1.22

The durations are −2 s, 0 s and 8 s, giving False, True, True with >=. The strict test > excludes the equality case, so its middle result becomes False. From −5 s to −2 s, three seconds elapse and the request is allowed. The clock readings' signs depend on a chosen time origin; their difference determines which event is later. Restore the inclusive test before continuing.

1.20 Let the condition choose the action

Printing a Boolean tells us the answer to a question, but does not yet use it to control the calculation. An if statement lets us execute some instructions only when a condition is true. An else provides the alternative path. We can now connect our stated domain rule to the program's behaviour.

Example 1.18 · Calculate or explain why not

# Fixed laboratory origin; positive direction is right.
# Constant rate is assumed from t0_s onwards.
x0_m = -2.0
v_m_per_s = 0.75
t0_s = 12.0
t_s = 20.0

elapsed_s = t_s - t0_s
if elapsed_s >= 0.0:
    x_m = x0_m + v_m_per_s * elapsed_s
    print("Predicted position:", x_m, "m")
else:
    print("No prediction: time is before the initial event.")

For the supplied inputs, the condition is true, so Python calculates and prints a position of 4.0 m. If we change the request to 10 s and run the complete cell again, only the explanatory message is printed. The program makes no new position prediction for that request.

The colon ends the line that introduces each branch. The following indented lines form its body: the instructions controlled by that branch. We use four spaces for each indentation level. Both the calculation and its output belong inside the permitted branch. The else lines align with the if; only one of the two bodies runs for each evaluation of the condition.

Indentation is part of the program, not decoration. Moving the final-position print outside the branch would make it run after either path. In a fresh session, an earlier request might then produce NameError because no position was assigned. In an old session, the name might still refer to a previous prediction and print a misleading stale value. A branch that does not assign x_m does not erase an earlier assignment. Keeping the calculation and the output together prevents that old result being presented as a new one.

Do not replace the negative duration with zero merely to make the calculation proceed. That would quietly answer a different question: the position at the initial event instead of the requested earlier time. A clear refusal preserves the distinction between an input we have rejected and a valid prediction. Later we can deliberately choose other policies, but we must explain them.

In the notebook, keep the correctly indented version as your final program and restart before checking it again. Allow about twenty minutes.

Discussion of Activity 1.23

The earlier time gives the refusal message; the initial event gives −2.0 m; the later event gives 4.0 m. A print outside the branch runs regardless of the condition. Its result then depends on whether x_m was assigned during this run or remains from a previous one. The correctly placed print belongs in the same branch that creates the new prediction. The zero-time case verifies inclusion of the boundary; testing only 20 s would not reveal an accidental strict comparison.

A wider view · optional reading

Decisions need a description of the surroundings

The rover's navigation problem involves interpreting observations and selecting a route around hazards. Our time comparison is far simpler and is not a model of that navigation software. The useful connection is that a computer's choice depends on how a question has been represented. A condition must say what is being tested; the meaning and adequacy of that test still need scientific and engineering judgement.

1.21 Keep several requests in an ordered list

Suppose we want positions at clock readings of 12 s, 16 s, 20 s and 24 s. Four separate names would work, but they would hide the fact that these values have the same role. A list keeps an ordered collection of values under one name. Square brackets enclose its items, with commas separating them.

Example 1.19 · A value and its place in the list

times_s = [12.0, 16.0, 20.0, 24.0]
print(times_s)
print(times_s[0])
print(times_s[2])
print(len(times_s))

The outputs are the complete list, then 12.0, then 20.0, then 4. Python numbers the positions in a list starting at zero. The number inside times_s[2] is an index: it selects the third item. It is not a requested time of 2 s. The built-in function len gives the number of items, which is four here.

There are four items, but no item at the non-negative index 4: the last is at index 3. Asking for times_s[4] raises IndexError. This is a different issue from a time-domain refusal. The index error says we asked for an item outside the list; it says nothing about whether a particular physical time is allowed. An empty list is written []; it has length zero and no first item.

Our list contains clock readings in seconds by convention. Python lists can hold different kinds of values, but that flexibility would not justify mixing seconds with metres in times_s. The list also allows repeated values. Two requests at the same time remain two entries unless we deliberately decide to combine them.

A list can be changed. For example, times_s[1] = 18.0 replaces its second item. There is one important difference from the numeric examples of Lesson 3: assigning other_times_s = times_s gives another name to the same list, not a separate list of copied items. Changing an item through either name affects what both names show. For this lesson's independent trials, enter a fresh list literal in each complete cell. We will return to copying collections when it is needed.

Use times_s = [20.0, 12.0, 20.0]. Predict its length, its first value and the value at index 2. Are the requests in chronological order? Replace the second entry with 16.0 and predict the whole list before running. Finally explain why indexing an empty list cannot supply an initial time. Allow about fifteen minutes.

Discussion of Activity 1.24

The length is 3; the first value and the value at index 2 are both 20.0. Repetition does not remove either entry. The sequence goes from 20 s back to 12 s and then to 20 s, so it is not chronological. Replacing index 1 gives [20.0, 16.0, 20.0]. An empty list has no stored requests. We must obtain the model's initial clock reading from its explicit input, not assume that the first requested time defines it.

1.22 Repeat the calculation, not a previous answer

With the requests collected, we could copy the position calculation four times and substitute a different list item each time. That would invite inconsistent edits. A for loop instead takes one item at a time and executes the same body of instructions for it. A single pass through the body is called an iteration.

Start with the four permitted times from Example 1.19 so that we can study repetition separately from rejection. We will combine the two ideas in Section 1.24. The physical equation is unchanged:

x=x0+v(t−t0)

Example 1.20 · One body, four requests

x0_m = -2.0
v_m_per_s = 0.75
t0_s = 12.0
times_s = [12.0, 16.0, 20.0, 24.0]

for t_s in times_s:
    elapsed_s = t_s - t0_s
    x_m = x0_m + v_m_per_s * elapsed_s
    print("Time:", t_s, "s; position:", x_m, "m")

Read the first line of the loop as “for each value in times_s, use that value as t_s and run this body”. On the first iteration, t_s is 12.0; on the second it is 16.0, and so on. It takes the values in the list, not their indices. Both the elapsed time and position must be recalculated inside the body.

The output contains four labelled rows. Their positions are −2.0 m, 1.0 m, 4.0 m and 7.0 m. The time label is as important as the position: it tells us which request produced which result.

This last distinction is easy to miss. The model gives the displacement since the fixed initial clock reading. Replacing x0_m with the preceding result would add that displacement again to an already advanced position. We are evaluating an explicit formula at requested times, not yet building a simulation that advances a state through small time steps.

Python follows the list's order. It neither sorts the requests nor waits for time to pass in the real world. If a list starts at 24 s and then asks for 12 s, the program evaluates those cases in that order. With an empty list the body runs zero times. After a non-empty loop, t_s and x_m remain associated with their last values, but they do not contain the earlier results. Relying on them after an empty loop could instead reveal an old value from the session or an undefined name.

As with a branch, the colon and indentation identify the body. A print at the left margin runs only after the loop finishes, not once per request. More subtly, moving the elapsed-time calculation outside the loop can leave every iteration using one old duration. A program can repeat a mistake perfectly; the trace is how we check what it repeats.

Using the same initial position, rate and initial time, predict the outputs for [20.0, 12.0, 20.0]. Write a three-row trace and run a complete loop to check it. Then try an empty request list. Explain why repeated requests produce repeated outputs and why an empty list should produce no prediction rows. Allow about twenty minutes.

Discussion of Activity 1.25

The durations are 8 s, 0 s and 8 s, giving positions 4 m, −2 m and 4 m in that order. Each prediction refers to the original initial event; the loop's order is not the physical history of the trolley. The repeated 20 s request is evaluated twice. For an empty list there is no iteration and therefore no printed row inside the loop. Do not interpret the absence of rows as a predicted position of zero.

1.23 Keep a result for each case

Printed rows are useful to read, but later calculations need accessible values. The name x_m is reassigned on every iteration, so it cannot by itself retain the history of predictions. We can collect those values in a new list, beginning with an empty list before the loop.

The instruction positions_m.append(x_m) adds the current value of x_m to the end of that list. The dot asks for an operation associated with the list, called a method. Here append takes one item, supplied in parentheses. We use it as an instruction that changes the list; do not assign its return value back to positions_m. That return value is None, not the updated list.

Example 1.21 · Build the result list once per run

x0_m = -2.0
v_m_per_s = 0.75
t0_s = 12.0
times_s = [12.0, 16.0, 20.0, 24.0]
positions_m = []

for t_s in times_s:
    elapsed_s = t_s - t0_s
    x_m = x0_m + v_m_per_s * elapsed_s
    positions_m.append(x_m)

print("Times / s:", times_s)
print("Positions / m:", positions_m)

The result list is [-2.0, 1.0, 4.0, 7.0]. After the first pass it contained only −2.0; after the second it contained −2.0 and 1.0. Appending a new number does not replace the earlier entries. With these permitted inputs, item 2 in the time list and item 2 in the position list belong together: 20 s and 4 m.

Notice the placement of the empty-list assignment. It must run once at the start of each complete calculation. Inside the loop it would discard earlier results on every pass, leaving only the last appended value. If it were omitted when rerunning the loop in a notebook, the new predictions could be appended to the previous run's list. Running the complete cell, including initialisation, makes the intended result independent of that history.

Our correspondence between list entries depends on adding one position for every requested time, in order. It is not guaranteed merely because the lists have convenient names. In the next section some requests will be rejected. We will then retain the corresponding accepted times alongside their positions, so a removed request cannot shift the apparent pairings.

Discussion of Activity 1.26

Initialising inside the loop leaves [7.0]: each pass discards all earlier predictions. Appending a second complete set without reinitialising gives [-2.0, 1.0, 4.0, 7.0, -2.0, 1.0, 4.0, 7.0]. Correct initialisation is outside the loop but inside the complete block that you rerun. With no requests, it produces []. That explicitly records no predictions; it does not leave a misleading last position as the result collection.

1.24 Combine repetition with an explained decision

We can now handle a batch containing earlier, initial and later times. On each pass, calculate the current elapsed time and choose the appropriate branch. For an accepted request, append both its time and its newly calculated position. For a rejected request, print its time with a reason. This keeps the result pairings explicit and makes refusals visible.

Example 1.22 · Preserve the pairing when a request is rejected

# Fixed origin, positive right; rate assumed from t0_s onwards.
x0_m = -2.0
v_m_per_s = 0.75
t0_s = 12.0
times_s = [12.0, 10.0, 16.0, 20.0]
accepted_times_s = []
positions_m = []

for t_s in times_s:
    elapsed_s = t_s - t0_s
    if elapsed_s >= 0.0:
        x_m = x0_m + v_m_per_s * elapsed_s
        accepted_times_s.append(t_s)
        positions_m.append(x_m)
    else:
        print("No prediction at", t_s, "s: before initial event.")

print("Accepted times / s:", accepted_times_s)
print("Positions / m:", positions_m)

The program reports the rejected 10 s request and retains [12.0, 16.0, 20.0] alongside [-2.0, 1.0, 4.0]. Pairing the three positions with the first three entries of the original request list would incorrectly attach 1.0 m to 10 s. Retaining the accepted times prevents that loss of meaning.

The if is indented because it is performed once per iteration. Its body is indented one level further because it runs only for an allowed request. The else aligns with this if, while the final list prints return to the left margin and run after the loop. There is one loop containing one decision, not a separate loop for every branch.

We have deliberately checked only one condition. A non-negative duration does not establish that the rate is correctly measured, that the units were converted, or that the trolley avoids a track end. It also does not imply a positive displacement: a negative signed rate gives motion in the negative direction during a positive duration. Keep the stated scope of a program separate from claims that it validates every input or physical assumption.

Before the independent task, consider why the boundary check is informative. At the initial event the duration vanishes, so the equation reduces to

x=x0+v×0=x0

This checks both the formula and the decision to include equality. A request just before that event tests the other branch. A later request with negative rate tests a different possible misunderstanding. No one example tests all three.

Discussion of Activity 1.27

The 4 s request is earlier than the initial event and is rejected. The accepted times are [9.0, 5.0, 7.0, 9.0]; their elapsed times are 4 s, 0 s, 2 s and 4 s. At −0.50 m/s the displacements are −2 m, 0 m, −1 m and −2 m. Adding the initial position gives [1.0, 3.0, 2.0, 1.0]. A suitable complete program is:

# Fixed laboratory origin; positive direction is right.
# Stipulated constant rate applies from the initial event onwards.
x0_m = 3.0
v_m_per_s = -0.50
t0_s = 5.0
times_s = [9.0, 4.0, 5.0, 7.0, 9.0]
accepted_times_s = []
positions_m = []

for t_s in times_s:
    elapsed_s = t_s - t0_s
    if elapsed_s >= 0.0:
        x_m = x0_m + v_m_per_s * elapsed_s
        accepted_times_s.append(t_s)
        positions_m.append(x_m)
    else:
        print("No prediction at", t_s, "s: before initial event.")

print("Accepted times / s:", accepted_times_s)
print("Positions / m:", positions_m)

The first and fourth retained predictions both belong to 9 s and both equal +1 m. At 5 s the equality boundary returns the initial +3 m. Positive positions are compatible with a negative rate: the point is still right of the origin while moving towards smaller coordinates.

For an empty input list, both output lists are empty and there are no refusal messages because there are no requests. For [3.0, 4.0], both lists are also empty, but there are two explicit refusal messages. The same empty collection can arise for different reasons; preserve the accompanying information. The time test checks our adopted lower time boundary, not the physical constancy of the rate or the full validity of the inputs.

The lesson has added two ways to organise instructions, while preserving their physical interpretation. A condition selects a path for a stated reason. A loop repeats a body for successive values, and a result list preserves the outputs that would otherwise be overwritten. In each case the trace tells us what happened; units, assumptions and captions tell us what it means.

In Lesson 5 we will package the model calculation as a function with explicit inputs and a returned result. That will let us reuse a named operation without copying its implementation each time. The distinctions established here—validity conditions, boundary cases, output pairings and reproducible execution—will make that next step much easier to inspect.
