Lesson 3
From a calculation to a readable program

A calculation can give the right answer and still be difficult to trust. Someone returning to it needs to know what the numbers mean, which assumptions they express, and what must be run again when an input changes. In this lesson we turn the short motion calculation from Lesson 2 into a program that another reader—including your future self—can inspect.

We will keep the physics deliberately familiar. The new work is to distinguish a mathematical relationship from an instruction, follow the values that instructions produce, and organise the calculation so that its result can be reproduced. The most revealing mistake will be a program that runs without an error but prints an answer belonging to an earlier set of inputs.

Allow three hours, including two hours working in the Lesson 3 notebook. The activities and notebook are the same work, not two separate exercise sets. A plain Python companion contains the runnable examples. Use the environment from the practical orientation; no additional packages are needed. If the syntax is already familiar, concentrate on the trace, deliberate faults and independent physical interpretation rather than skipping those checks.

1.13 Let the program reveal the model

In Lesson 2, a marked point on a trolley had position −2 m at a clock reading of 12 s. Its stipulated constant signed rate was +0.75 m/s. At 20 s, eight seconds had elapsed, so its change in position was +6 m and its position was +4 m. Positions were measured from a fixed laboratory origin, with positive direction to the right. Those choices gave meaning to the model

x=x0+v(t−t0)

A Python expression can compress the numerical work into a single line. But compression hides decisions. Is the first number a position or a change? Do the clock readings use the same origin? Is the rate expressed in metres per second? Splitting a calculation into meaningful stages makes these questions easier to answer, even when it adds lines.

Example 1.11 · Make the stages visible

Write the trolley calculation so that a reader can identify the inputs, elapsed time, displacement and final position without reconstructing one long expression.

x0_m = -2.0
v_m_per_s = 0.75
t0_s = 12.0
t_s = 20.0

elapsed_s = t_s - t0_s
displacement_m = v_m_per_s * elapsed_s
x_m = x0_m + displacement_m
x_m
Reading the solution

The first four lines give the case we intend to calculate. The next three follow the physical reasoning: find a duration, multiply by a rate, then add the resulting displacement to the initial position. The last line displays the final value when it is the last expression in a notebook cell. The intermediate values are 8.0, 6.0 and 4.0; their names tell us to interpret them in seconds, metres and metres respectively.

We have introduced displacement_m to give the signed change its own name. This is the same model and arithmetic as before. The extra name exposes a stage that is useful to inspect; it does not add a new physical assumption.

Our names use letters, digits and underscores, beginning with a letter. Python distinguishes upper and lower case: t_s and T_s are different names. Spaces and minus signs cannot join words in a name; use an underscore, as in elapsed_s. Avoid names such as print that already identify tools we use. You do not need a catalogue of every naming rule to write these examples, but you do need to reproduce each chosen name consistently.

A useful name identifies a quantity and, where appropriate, its numerical unit. The suffix _m is a promise made by the author, not a conversion performed by Python. Assigning a centimetre value to x0_m would break that promise while remaining valid code. Readability helps us notice such a mistake; it cannot make the mistake impossible.

Activity 1.16 · Read before running

In the notebook, enter Example 1.11 and predict its three intermediate results before running it. Then change the initial position to −3 m, leaving the rate and clock readings unchanged. Which intermediate results should change? Run the entire cell and explain the new position. Use about ten minutes for prediction, execution and interpretation.

Discussion of Activity 1.16

The original duration is 8 s, displacement +6 m and position +4 m. Changing only the initial position leaves duration and displacement unchanged. The new position is −3 m + 6 m = +3 m. If a duration changed, the program would no longer represent the stated change of input. If the output remained 4.0, first check whether you actually executed the edited cell.

A wider view · optional reading

Scientific software has human readers

NASA’s description of this planning system explains how scientists and engineers coordinate proposed rover activities with limits on time, power and data. The calculation serves a decision made by people. Our trolley model is far simpler, but it shares the need to make inputs and results interpretable.

A future reader must be able to tell what a number describes before judging whether it is reasonable. Clear names, stated assumptions and meaningful output are therefore part of scientific communication, not merely preferences about how code looks.

1.14 Numbers in the model and numbers in Python

The model treats a duration as a physical quantity that could, in principle, take a fractional value. The program needs a numerical representation of that quantity. Python provides several kinds of value, called types. Two will carry most of our calculations here: integers, written without a decimal point, and floating-point numbers, usually written here with one.

8 is an integer value, of type int; 8.0 is a floating-point value, of type float. Both represent the number eight in these examples. The different spelling tells Python how the number is represented; it does not tell a physicist how accurately a duration was measured. A count of eight recorded events and a measured duration of eight seconds need different physical explanations even if both are initially entered as 8.

We can inspect the representation with the built-in tool type. A built-in function is an operation already supplied by Python. Writing its name followed by parentheses asks Python to perform it on the value inside. The function print displays what we ask it to display; unlike a bare final expression, it can show a result from any line in a cell or script. In print(type(8)), Python first obtains the type of 8, then prints that result.

Example 1.12 · The same value, different representations

print(type(8))
print(type(8.0))
print(9 / 4)
print(8 / 4)

The output is:

<class 'int'>
<class 'float'>
2.25
2.0

The first two lines identify the types. With the built-in numeric types used here, / performs division and returns a float even when the quotient is a whole number. Thus the fourth result is 2.0. It does not mean that the division has acquired uncertainty, nor that a measurement is accurate to a tenth.

Integers are useful for exact whole-number counts. Floats allow fractional inputs and are convenient for quantities such as position and elapsed time. Arithmetic mixing an integer and a float normally produces a float: 8 + 0.5 gives 8.5. We will usually write model inputs with decimal points to allow fractional cases without changing our presentation. This is a convention for readable code, not a requirement that all physical inputs be floats.

There is a limitation behind the word “floating”. A computer float has finite precision and usually stores a binary approximation to a decimal value. Some fractions, such as one half or three quarters, have exact binary representations; many others, including one tenth, do not. You can expose this by running print(0.1 + 0.2), which on the ordinary Python environment used here displays 0.30000000000000004. The tiny difference from 0.3 concerns numerical representation, not an extra physical effect. Detailed error analysis comes later. For now, do not invent measurement precision from displayed digits or change a physical model merely to hide a final decimal digit.

Keep three questions separate

What physical quantity does the value describe? In what unit is its numerical value expressed? How is that number represented by Python? A type answers the third question. It answers neither of the first two.

Activity 1.17 · Predict the type and the meaning

Before running the cells in the notebook, predict the values and types of 12 - 4, 12.0 - 4 and 9 / 4. Then use print and type to check. If the first two expressions both describe an elapsed time in seconds, does either spelling establish a more precise measurement? Finally inspect 0.1 + 0.2 and write what its extra digits do—and do not—show. Allow about fifteen minutes.

Discussion of Activity 1.17

The results are 8 of type int, 8.0 of type float, and 2.25 of type float. Subtraction of these two integers remains integer arithmetic; introducing the float changes the representation. Neither spelling establishes instrument resolution or measurement uncertainty. The final digits in the decimal-sum example arise from floating-point representation and arithmetic. They do not describe an observed physical deviation.

1.15 Assignment is an event

In mathematics, the equation relating position and time remains a relationship: when we choose a different time, we can use it to calculate the corresponding position. A Python assignment has a different role. When Python executes x_m = x0_m + displacement_m, it evaluates the expression on the right using the values available at that moment, then associates the result with the name on the left.

This order matters. The name does not retain the expression as a live formula. In our numeric calculation, x_m refers to the resulting number. Later changing x0_m or displacement_m does not make Python repeat the earlier instruction. The equation in our reasoning still relates the quantities, but we are responsible for executing the instructions that implement it.

Example 1.13 · An answer from an earlier duration

Predict both printed results before following the trace in Figure 1.15.

v_m_per_s = 0.75
elapsed_s = 8.0
displacement_m = v_m_per_s * elapsed_s
elapsed_s = 12.0
print(displacement_m)
displacement_m = v_m_per_s * elapsed_s
print(displacement_m)

The first printed value is 6.0. It was calculated when the duration was 8 s. Assigning 12.0 to elapsed_s changes that one name, but does not execute the multiplication again. The second multiplication does use the new duration, and the final printed value is 9.0. Both outputs follow Python’s rules; only the second is the displacement for 12 s at the stated rate.

Call the first displacement stale relative to the new duration: it belongs to an earlier input. Python cannot identify that scientific mismatch from these names. A stale result may look plausible and produce no error message, which is why following the calculation is more informative than merely asking whether it runs.

The evaluate-then-assign rule also explains a line that would be strange as an algebraic equation: elapsed_s = elapsed_s + 1.0. If the name currently refers to 8.0, Python evaluates 8.0 + 1.0 and then associates 9.0 with the same name. It does not assert that a number equals itself plus one. The old value must already exist; in a fresh session, using an unassigned name on the right produces NameError.

Activity 1.18 · Preserve an earlier value

Trace the following on paper, then run it in the notebook. Explain why the two final numbers differ. Modify the final assignment to t_s once more and predict whether saved_t_s changes. Allow about twenty minutes, including tracing Example 1.13.

t_s = 20.0
saved_t_s = t_s
t_s = t_s + 4.0
print(t_s)
print(saved_t_s)
Discussion of Activity 1.18

The output is 24.0 followed by 20.0. The second line associates saved_t_s with the numeric value available then, 20.0. Reassigning t_s to 24.0 does not reassign saved_t_s. Changing the increment to 6.0 and rerunning the whole cell gives 26.0 and 20.0. This explanation concerns the numeric values used here; later, collections will require additional care about shared objects.

1.16 The page and the running session

A notebook presents code in a visible order, but lets you execute cells in another order. The running Python process, called the kernel, keeps the values established by executed instructions. Editing text in a cell changes the document. Running the cell sends those instructions to the kernel. Those are separate actions, and neither the page order nor the appearance of the text is a complete record of what has happened.

Suppose the first cell assigns the four trolley inputs, the second calculates elapsed time and position, and the third prints x_m. After all three have run, you edit t_s = 20.0 to t_s = 24.0. If you do not run the first cell, the kernel still has the old time. If you run only the first and third cells, the time changes but the stored position does not. The second cell must run again after the input changes and before you print its new result.

Example 1.14 · Repair the whole chain

A learner runs the original trolley calculation, then changes the final clock reading to 24 s and executes the input cell. The display still shows 4.0. Should they change the displayed number by hand?

Solution

No. Recalculate the duration and all quantities that depend on it. The new duration is 24 s − 12 s = 12 s, the displacement is 0.75 m/s × 12 s = 9 m, and the position is −2 m + 9 m = +7 m. Running the calculation cell followed by the display cell produces 7.0.

Re-running only the final position line can also be insufficient if that line uses a stored displacement_m which is itself stale. Follow the chain from the changed input. For a short calculation, rerunning the complete input-and-calculation sequence is usually clearer than trying to remember which individual lines need attention.

Notebook execution counters are useful clues to order, but they are not proof that the visible text produced the visible output: a cell may have been edited since its last execution. Nor does saving a notebook rerun its calculations. The saved document may contain code, text and earlier outputs; it is not a guarantee that another person can reproduce the result from the visible code.

A stronger check is to save your work, restart the kernel and run all code cells from top to bottom. Restarting removes the session’s stored names, so hidden dependencies on earlier experiments become visible. Use your notebook application’s restart-and-run-all action, or restart and then run all cells in order; wording varies between applications. Do not confuse clearing displayed output with restarting Python. If the clean run fails, identify the first failing cell and repair the missing definition or order rather than reviving an unexplained old value.

Activity 1.19 · Produce and repair a stale result

The notebook contains cells A, B and C from Figure 1.16. Run A, B, C once with the original 20 s input. Edit A to use 24 s and run C only; then run A and C; finally run B and C. Predict and record each result before checking it. Finish by restarting and running all cells in order. Allow about twenty-five minutes to investigate, repair and explain.

Discussion of Activity 1.19

The initial output is 4.0. Editing A and running only C still gives 4.0 because the new input has not executed. Running A then C also gives 4.0: the new time is stored, but the position has not been recalculated. Running B then C gives 7.0. With A visibly containing 24.0, a clean top-to-bottom run also gives 7.0. The explanation must identify both possible gaps: edited text that has not run, and dependent calculations that have not run again.

1.17 Explain the choices, label the result

Names help us follow the arithmetic, but they cannot express every physical decision. A comment can state the reference direction or explain why a conversion is present. In Python, a # outside quotation marks begins a comment extending to the end of the line. Python does not execute that comment. Use it to preserve reasoning that is otherwise easy to lose.

A comment saying “set time to twenty” beside t_s = 20.0 mostly repeats the line. A comment saying “clock readings use the same origin” records a condition that the subtraction needs. Both are legal; the second is more useful. Comments can also become out of date, so check them when you change the program. A convincing explanation beside the wrong code does not repair the code.

Example 1.15 · A small program with an interpretable output

# Fixed laboratory origin; positive direction is right.
# Constant signed rate is assumed throughout this interval.
x0_m = -2.0
v_m_per_s = 0.75
t0_s = 12.0
t_s = 20.0

# Both clock readings are in seconds, with the same origin.
elapsed_s = t_s - t0_s
displacement_m = v_m_per_s * elapsed_s
x_m = x0_m + displacement_m

print("Elapsed time:", elapsed_s, "s")
print("Predicted position:", x_m, "m")

This produces:

Elapsed time: 8.0 s
Predicted position: 4.0 m

Text inside quotes is a string: a sequence of characters. Here the strings supply labels and units. The commas separate the items passed to print, which normally places a space between them and ends each call with a new line. By contrast, print("x_m") would print the name as text, not the value associated with it.

Writing “Predicted” matters: this value follows from our assumed constant rate. We have not measured the final position. Printing “m” labels the value but does not check or convert its unit. The argument justifying the label still belongs to us.

When a result is wrong, ask at which level the explanation first fails. A SyntaxError means Python could not parse an instruction—for example, because a quote or parenthesis is missing. A NameError means a name needed during execution was not defined in that session, perhaps because of a spelling difference or a cell run out of order. A program with neither error may still use the wrong units, the wrong model or a stale intermediate value. Read the last line of an error message, inspect the indicated code and nearby lines, and make a change for a stated reason.

Activity 1.20 · Two faults, two explanations

A stipulated rate is +75 cm/s. A program copies Example 1.15 but changes its rate line to v_m_per_s = 75.0 and ends with print("x_m"). Explain each fault separately. Repair both and add a comment explaining the conversion. Run the repaired complete program in the notebook; allow about fifteen minutes.

Hint

First ask which numerical value belongs in a variable labelled metres per second. Then distinguish a name evaluated by Python from characters inside quotation marks.

Discussion of Activity 1.20

The numerical rate in metres per second is 75100=0.75. Use v_m_per_s = 75.0 / 100.0 with a comment such as # Convert centimetres per second to metres per second. Keeping 75.0 would predict −2 + 75 × 8 = 598 m; the program would run, but the units would be inconsistent with its names. Quoting "x_m" independently causes literal text to be printed. A corrected output line is print("Predicted position:", x_m, "m"), which displays 4.0 m after the corrected calculation. Fixing the label alone would not fix the rate.

1.18 Build a calculation that survives a fresh start

We now have the pieces of a readable scalar program: explicit inputs, understandable names, a sequence of calculations, comments that explain choices, and output that identifies the quantity. The final task is to combine them without relying on the earlier trolley cell. Typing an independent version matters because it asks you to decide what the inputs mean and which instruction depends on which value.

Example 1.16 · Choose a check before running

For any constant-rate case in this lesson, what position should the program return when the final clock reading equals the initial one?

Reasoning

The elapsed time is zero. The rate multiplied by zero gives zero displacement, so the predicted position is the initial position:

x=x0+v×0=x0

This expected result comes from the meaning of the model, not from an earlier program output. It is therefore a useful check on the translation into code. It cannot establish that the real object actually moves at a constant rate, and it will not detect every possible programming mistake. We choose several checks for different reasons.

Activity 1.21 · An independently readable calculation

A marked point on a conveyor is at −1.25 m when a clock reads 6 s. Over the interval of interest, its stipulated constant signed rate is +37.5 cm/s. Predict its position at a clock reading of 18 s. The origin is fixed beside the conveyor and positive is to the right. These are invented inputs for testing a model, not measured conveyor data.

Use about thirty-five minutes for the following integrated task. Before coding, convert the rate to metres per second and calculate the duration, displacement and position on paper. In a fresh notebook cell, write the program independently, including useful comments and labelled output. Then use separate complete versions of that cell to check: the initial event; zero rate; and the same magnitude of rate in the negative direction. Keep the ordinary case intact so your final document is unambiguous.

Add a short text-cell interpretation stating the coordinate convention, the meaning of the ordinary result and one physical limitation. Restart the kernel, run the notebook from top to bottom, inspect the results and save. Copy buttons are useful for experimenting with worked examples; this final task asks you to construct your own calculation.

Hint

The input rate is in centimetres per second, whereas the position input is in metres. Keep the initial clock reading explicit. For each check, state what should happen physically before calculating the numbers.

Discussion of Activity 1.21

The rate is 0.375 m/s. The elapsed time is 12 s, giving a displacement of +4.5 m and a position of +3.25 m. The positive result means the marked point is to the right of the fixed origin; it is not the distance travelled from the initial point.

# Fixed origin beside the conveyor; positive is right.
# Stipulated constant-rate case, not measured data.
x0_m = -1.25
v_cm_per_s = 37.5
v_m_per_s = v_cm_per_s / 100.0
t0_s = 6.0
t_s = 18.0

elapsed_s = t_s - t0_s
displacement_m = v_m_per_s * elapsed_s
x_m = x0_m + displacement_m

print("Elapsed time:", elapsed_s, "s")
print("Displacement:", displacement_m, "m")
print("Predicted position:", x_m, "m")

At the initial event (t_s = 6.0), the position is −1.25 m. With zero rate at 18 s it is also −1.25 m, but for a different reason: time passes without displacement. With v_cm_per_s = -37.5 and the original clock readings, the displacement is −4.5 m and position −5.75 m. Re-run the conversion as well as the motion calculation after changing the centimetre-per-second input.

A suitable limitation is that the chosen point must maintain the stipulated signed rate throughout the interval, with no stopping or reversal. A clean run establishes that the document supplies the values and order its calculation needs; it is not evidence that a physical conveyor follows those assumptions. Other clear names or a different division into cells are acceptable if the meanings, dependencies and checks are preserved.

A readable program makes the route from assumptions to result visible. A clean rerun makes that route repeatable without relying on forgotten session history. Together they give another reader a fair chance to inspect the calculation, challenge a choice and reproduce a result.

So far, you have chosen each case yourself and run it explicitly. In Lesson 4, the program will compare values, choose between actions and repeat a calculation for a small collection of inputs. The same habit will remain essential: predict what each instruction should mean, trace what it actually does, and interpret the result as a physical statement.
